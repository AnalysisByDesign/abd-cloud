# WP-04 Discovery: ECS Cluster, Host ASG and Capacity Providers

**Date**: 2026-11-11
**Scope**: read-only. Code in `abd-cloud`, `abd-cloud-modules`, `abd-cloud-params`, `abd-cloud-packer`, `configs` and `abd-cloud-containers` (WP-03 discovery). Read-only AWS calls in `abd-wordpress` (800653036500), eu-west-1, and a read of two Terraform state files in `abd-tf-state`. Memory figures from a `ps`/`free` snapshot that Dave ran on the production host.

## Summary

- **Almost nothing for ECS exists in AWS.** The `default` cluster is empty, there are no task definitions, Cloud Map namespaces or capacity providers of our own. The only other cluster is the image generator PoC's Batch cluster, which is off-limits.
- **Some ECS code exists, but it is a starting point rather than something to reuse as-is.** `compute/ecs-cluster` (params `app.ecs`, marked `prevent`) creates a bare cluster and has an empty state file. `compute/ecs-fargate` is 2019 code that would not plan today. The `ecs/service` module is awsvpc-only and the `ecs/task` module has no EFS or role split.
- **The ALB has no host-header rules.** The HTTPS listener (11 certificates) sends every hostname to one target group on the host's port 80, and nginx on the host does the virtual hosting. Cutover per site therefore means *adding* a host-header rule above the default, which is a clean pattern.
- **The database is a single MySQL 8.4 `db.t3.micro`** (not Aurora, not Multi-AZ), with a manually created parameter group. Peak connections over 14 days were 17, against a limit of at most about 85.
- **Secrets are in SSM Parameter Store**, including a whole `wp-config.php` per site. ECS `secrets` can read SSM directly, so the convention carries over, but the whole-file parameters are a WP-05 problem.
- **The host does more than the work package lists**: eight WordPress sites, Tulox (web, queue worker, Reverb, scheduler), mortgage.daverix.ai (Laravel), a postfix relay, and several cron jobs. There is no Valkey or Redis today.
- **Memory is not the constraint it was feared to be today**: the whole host uses about 0.8 GiB of 3.8 GiB. Splitting into per-site tasks duplicates nginx, PHP-FPM and OPcache per site, so ECS will need several times that. See section 7.
- **The reserved instance is a regional `t4g.medium`** (ends 2029-08-02), and it is fully used by the current host. Any ECS host runs on demand until the old host is retired, which breaches the £5 a month guardrail and needs a ruling (Q4).

## 1. ECS today

**AWS**: clusters `default` (ACTIVE, no instances, tasks or services, Container Insights off) and the PoC's `AWSBatch-poc-tulox-image-fleet-*`. No task definition families. No Cloud Map namespaces. Capacity providers are only the built-in `FARGATE` and `FARGATE_SPOT`. A stale log group `/ecs/first-run-task-definition` suggests the `default` cluster came from the console's first-run wizard.

**Code**:
- `tf-templates/compute/ecs-cluster/ecs.tf:6-11` calls `modules/compute/ecs/cluster` and nothing else. `outputs.tf` is empty, and its README claims capacity provider settings it does not have.
- Params `abd-wordpress/wordpress-vpc/app.ecs` (`ecs_config.sh`: state `abd-wordpress/compute/ecs-cluster`, `name = "cluster"`, which gives `abd-wordpress-cluster`). `sequence/prod.csv` has `4000,protect,prevent,…/app.ecs`. The state file `abd-wordpress/abd-wordpress/compute/ecs-cluster.tfstate` exists and holds **no resources** (written by Terraform 1.9.0 in May 2026).
- `tf-templates/compute/ecs-fargate` has no params target. Its state file (`compute/ecs-fargate.tfstate`, Terraform 0.11.14, 2019) holds **no resources**. The template would not plan: 0.11 interpolation in `alb.tf:11`, and references to `data.aws_vpc.vpc.id` on a counted data source (`security-groups.tf:15,50`). Reusable pieces: the ecs-tasks assume-role document (`policy-documents.tf:7-21`), an execution role using `AmazonECSTaskExecutionRolePolicy` (`iam.tf:6-17`) and an awslogs container definition template (`files/task-defn.json.tpl`).

**Modules** (`abd-cloud-modules/compute/ecs/`):
- `cluster` (`main.tf:5-14`): cluster only. The containerInsights setting is commented out and `ecs_insights` is unused. Outputs name, id and arn.
- `service` (`main.tf:9-30`): always sets `network_configuration` (awsvpc only), one mandatory `load_balancer`, a hard-wired `launch_type` (which conflicts with `capacity_provider_strategy`). No circuit breaker, health check grace period, `ignore_changes` on `task_definition`, placement constraints, service registries or tags. Outputs only the id.
- `task` (`main.tf:9-18`): one variable feeds both `execution_role_arn` and `task_role_arn`. `requires_compatibilities` is a single string. No volumes and no tags.
- Callers: `ecs-cluster` (cluster only) and the dead `ecs-fargate`. Changing `service` and `task` therefore has no live caller to protect.

## 2. Hosts: the ASG and launch template path

The ECS hosts would naturally be another params target on `tf-templates/compute/ec2-asg`, as the NAT instance is. `enable_load_balancer = false` already turns off the ALB, its target group and its security group rules (`alb.tf:8`, `security-groups.tf:12-75`), and the RDS and EFS rules are gated on `rds_security_group` and `efs_security_group` (`security-groups.tf:100-147`).

What WP-01 already gives: subnet tier (`asg_subnet_tier`, default `private_app`), AZ filtering, lifecycle hooks, launch-before-terminate refresh settings (min 100, max 110), the EventBridge Scheduler weekly refresh (`scheduled-refresh.tf`), and the no-InService and status-check alarms to `abd-alerts` (`alarms.tf`, gated on `enable_alarms`). User data is rendered with `extra_template_vars` plus computed values, so an ECS cluster-join script needs no module change.

Gaps for ECS hosts:
- **AMI by SSM parameter.** `data-sources.tf:48-62` looks AMIs up by name glob and owner only. The ECS-optimised AL2023 arm64 AMI is published at `/aws/service/ecs/optimized-ami/amazon-linux-2023/arm64/recommended/image_id` (today `ami-063aa0db5ac7f1263`). Launch templates accept `resolve:ssm:<parameter>` as the image, resolved at each launch, which fits the weekly refresh (Q3).
- **Instance role.** The `security/iam-role` module takes one `policy_arn`. `ec2-asg/iam.tf` attaches `CloudWatchAgentServerPolicy`, SSM core and an optional templated policy. `AmazonEC2ContainerServiceforEC2Role` needs another attachment.
- **`asg` module** (`abd-cloud-modules/compute/asg`): no `protect_from_scale_in` (needed for managed termination protection), no `capacity_rebalance` or `mixed_instances_policy` (spot phase), and the `launch_template` block is static (`main.tf:12-15`), so it must become dynamic for mixed instances. The `instance_refresh` preferences have no `scale_in_protected_instances`: its API default is `Wait`, which makes a refresh **fail after an hour** when ECS managed termination protection is on. Both the ASG block and the scheduled refresh input need `Refresh`.
- **`AmazonECSManaged` tag**: can be added through `ec2-asg`'s tag map (`autoscaling-group.tf:35-44`) without a module change.
- **`launch-template` module**: no `metadata_options`. AL2023 AMIs default to IMDSv2 with a hop limit of 2, which lets bridge-mode containers reach the instance role's credentials; a hop limit of 1 blocks that. `credit_specification = unlimited`, `ebs_optimized` and `instance_initiated_shutdown_behavior = "stop"` are hard-coded (`main.tf:10-11,36-38`); credits must become optional before the spot phase. `common_tags` is accepted but unused (no `tag_specifications`).
- **Key pair** is always registered (`keypairs.tf:4-10`); harmless, as for the NAT.

## 3. ALB

**AWS**: one internet-facing ALB, `abd-wordpress-ec2-asg`, security group `abd-wordpress-ec2-asg-alb` (80 and 443 from `0.0.0.0/0`). Listener 80 redirects to 443. Listener 443 (`ELBSecurityPolicy-TLS13-1-2-2021-06`, 11 certificates) has **only its default action**, forwarding to target group `abd-wordpress-ec2-asg` (HTTP 80, instance targets, health check `/license.txt` on port 80, matcher 200/301/302, interval 60 s, healthy threshold 2). The host is the one healthy target.

**Code**:
- `abd-cloud-modules/compute/alb/main.tf` builds the ALB, both listeners and the single target group in one module, called from `ec2-asg/alb.tf:5-23`. The target group's port and health-check port are hard-coded to 80. Outputs include the 443 listener ARN, but not the ALB ARN, its `arn_suffix` or its security group. Access logs are commented out.
- Per-site certificates and DNS live in `tf-templates/network/dns` (params `hosted-sites/<site>`), which finds the ALB by name (`format("%s-%s", vpc, "ec2-asg")`) and its 443 listener (`data.tf:10-19`), then adds `aws_lb_listener_certificate` (`load-balancer.tf:4-9`) and alias records. **New service target groups and listener rules can find the listener in the same way**, without touching the ALB module.
- `ec2-asg/ssl-cert.tf:5-21` gives the ALB a base certificate for `abd-wp.uk` and `*.abd-wp.uk`, so a test hostname under `abd-wp.uk` needs no new certificate.
- ALB to host: TCP 80 only, as a paired egress and ingress rule (`ec2-asg/security-groups.tf:59-83`). Dynamic host ports need an ephemeral range pair; `security-group-rule-link` already supports `from_port` and `to_port`.
- Target group names are capped at 32 characters; `abd-wordpress-` uses 14.

## 4. EFS

**AWS**: one file system, `fs-38536ff0` (`abd-wordpress-html`), about 2 GB, general purpose, **bursting** throughput, encrypted, IA after one day without access. Mount targets in all three AZs (private_db subnets), security group `abd-wordpress-html-efs` (2049 from the host's security group only). **No access points and no file system policy.**

**Code**: `tf-templates/storage/efs` (params `wordpress-vpc/storage`), with a CNAME `efs-html` in the private zone. The module outputs no mount target or access point information. The host mounts the file system root at `/mnt/efs` over TLS, with the ID hard-coded in `app.wordpress/files/cloud-init.sh:6-13`.

**Layout and ownership** (from `abd-cloud-packer/builds/wp-stack-ami`):
- `uploads/<site>`, `w3tc-config/<site>`: symlinked into each site's `wp-content`.
- `tulox.uk/storage`: Tulox's `storage/app` is a symlink to it (`files/tulox-init.sh:85-91`); `mortgage.daverix.ai/storage` likewise (`mortgage-init.sh:53-59`).
- Config also lives on EFS and is bind-mounted over `/etc`: `config-php83/{php.ini,php.d,php-fpm.conf,php-fpm.d,nginx}` and `config-php85/...`. Also `manifests/<site>.json`, `premium-plugins/`, `premium-themes/` and `config-postfix/`. Containers bake config into the image instead (WP-03), so only uploads and application storage need access points.
- Everything runs as the AL2023 `nginx` user and group (numeric IDs not verified), with `chown -R nginx:nginx` at boot. The WP-03 images use 10001:10001. **Existing files will need a one-off ownership change, or access points that present them as 10001**, when each site moves (WP-05).

## 9. Gaps against the target

1. Cluster with outputs, and a capacity provider with managed scaling, managed termination protection and managed draining, plus the cluster's default strategy.
2. ECS host target: ECS-optimised AL2023 arm64 AMI, `AmazonEC2ContainerServiceforEC2Role`, cluster-join user data, IMDS hop limit 1, `protect_from_scale_in`, `AmazonECSManaged` tag, and refresh with `scale_in_protected_instances = Refresh`.
3. ALB to host security group pair on the ephemeral port range.
4. Service pattern: target group (health check on `traffic-port`), host-header listener rule, service with capacity provider strategy, circuit breaker with rollback, `ignore_changes` on `task_definition` (if Q6 goes that way), log group, task role.
5. Shared task execution role: ECR pull (`ecr-pull-abd` from WP-02), logs, and `ssm:GetParameters` plus `kms:Decrypt` for the service's SSM prefix.
6. EFS access points per site (none exist), and EFS volume support in the task module.
7. Alarms for service health and deployment failure.
8. Log retention as a variable.

## 10. Risks

- **Overlap cost**: an ECS host is entirely on demand until the old host goes. Keep the overlap short (Q4).
- **Refresh blocked by scale-in protection**: without `scale_in_protected_instances = Refresh`, the weekly refresh fails after an hour, silently unless alarmed.
- **Instance role reachable from containers** if the IMDS hop limit is left at the AL2023 default.
- **Memory headroom** on one `t4g.medium` once all sites have moved; rolling deployments need room for one extra task.
- **Database connections**: per-site FPM pools multiply the possible connections against a limit of at most about 85 on `db.t3.micro`. Size `pm.max_children` per task in WP-05, and watch `DatabaseConnections`.
- **EFS bursting credits** with more clients; the file system is small (2 GB), so its baseline throughput is low.
- **Cluster registration order**: hosts that start before the cluster exists cannot register. The apply sequence must create the cluster first.
- **Ownership mismatch** between existing EFS files (`nginx`) and the images' 10001:10001 (WP-05).

## 11. Proposed approach (subject to rulings)

1. Modules, each backward compatible: `asg` (`protect_from_scale_in`, `scale_in_protected_instances`; `capacity_rebalance` and a dynamic launch template held for the spot phase), `launch-template` (`metadata_options`, optional credit specification), `ecs/cluster` (Container Insights wired, outputs), `ecs/service` (network configuration optional, capacity provider strategy, circuit breaker, grace period, placement constraints, tags, outputs), `ecs/task` (separate execution and task roles, volumes with EFS access points, tags), `monitoring/cloudwatch/group` (retention variable).
2. `ec2-asg`: optional AMI by SSM parameter, optional ECS instance policy, scale-in protection and refresh preference wiring. New params target for the hosts.
3. `ecs-cluster`: cluster, capacity provider and default strategy; un-prevent `app.ecs`.
4. A new service template, proven with a `hello` service on a test hostname, plus the deployment role and rollout workflow for CI.
5. EFS access point pattern (one for the hello service, per site in WP-05).
6. Alarms and the weekly refresh.
7. Later phase: spot ASG and capacity provider.

## 12. Questions for Dave (Phase 2)

1. **Cluster and hosts layout.**
   - Cluster: grow `compute/ecs-cluster` and reuse the `app.ecs` target (empty state, cluster `abd-wordpress-cluster`), removing `prevent`? Or a new template and name (the overview says `prod`)? Recommendation: reuse `app.ecs` and its name.
   - Hosts: a new params target on `ec2-asg` with `enable_load_balancer = false`. Proposed name `wordpress-vpc/ecs.hosts`; yours to choose.
   - Capacity providers: (a) in the cluster template, finding each host ASG by name, so one place owns the cluster's provider list and default strategy (sequence: cluster, then hosts, then a second cluster apply when a host ASG is added); or (b) in each host target, with the cluster's provider association in the cluster template. Recommendation: (a) with the cluster created before the hosts, because `aws_ecs_cluster_capacity_providers` is one resource per cluster and the spot ASG later adds a second provider.
2. **Modules.** Extend `asg`, `launch-template`, `ecs/cluster`, `ecs/service`, `ecs/task` and `monitoring/cloudwatch/group` as in section 11, or create new ECS modules? And retire the `ecs-fargate` template (and its empty 2019 state file)? Recommendation: extend all; retire `ecs-fargate`.
3. **Host AMI.**
   - (a) ECS-optimised AL2023 arm64 through `resolve:ssm:` in the launch template: resolved at each launch, so every weekly refresh picks up the latest AMI with no Terraform change.
   - (b) The same parameter read by a data source at plan time: every AMI release shows as a plan diff.
   - (c) A Packer-baked AMI built on it.

   Recommendation: (a).
4. **Host size and overlap cost.** Both options breach the £5 a month guardrail while the old host runs.
   - (a) `t4g.small` for WP-04 (hello service only, about $13 a month), resized to `t4g.medium` when WP-05 starts moving sites.
   - (b) `t4g.medium` from the start (about $27 a month).
   - (c) `t4g.large` from the start (about $54, falling to about $27 once the RI covers half).

   Recommendation: (a), then `t4g.medium` for the migration; revisit `t4g.large` if WP-05's measured reservations exceed about 3 GiB.
5. **Service structure** (the biggest structural ruling).
   - (a) One reusable service template (proposed `tf-templates/compute/ecs-service`) with one params target per service (for example `wordpress-vpc/svc.hello`, later `svc.<site>`). Terraform owns the target group, listener rule, service, log group, task role and the task definition's shape (ports, environment, secrets, volumes, memory).
   - (b) Per-application templates (one for WordPress sites, one for Tulox) owning several services each.
   - (c) Terraform owns only the service shell; each application repository owns its whole task definition.

   Recommendation: (a). It matches the repository's template-plus-params pattern and keeps one place to look for each service.
6. **Deployment ownership.**
   - (a) Terraform owns everything, including the image digest. Each rollout is a params change and an apply by Dave, which rules out unattended nightly rollouts.
   - (b) Terraform registers the task definition but ignores `task_definition` on the service. CI takes the family's latest revision, swaps only the image digest, registers it and updates the service. A Terraform shape change takes effect at the next rollout (or by a runbook `update-service`).

   Recommendation: (b).
7. **Nightly rollout trigger and CI access.**
   - Trigger: (a) each image repository runs a reusable rollout workflow at 04:00 after its smoke test; (b) one orchestrating workflow rolls out every service. Recommendation: (a), with the reusable workflow in `abd-cloud-containers`; WP-04 proves it on the hello service.
   - CI needs a deploy role (OIDC): `ecs:RegisterTaskDefinition`, `ecs:UpdateService`, `ecs:DescribeServices` and `iam:PassRole` on the task and execution roles. Extend `security/github-deploy` with an `ecs_deploy_roles` map, like WP-02's `ecr_push_roles`? Recommendation: yes.
8. **How tasks reach Valkey.** Tulox has no Valkey today (queue, cache and sessions use the database), so nothing in WP-04 needs it.
   - (a) One Valkey task in `awsvpc` mode with a Cloud Map private DNS **A record**. One ENI is affordable (a `t4g.medium` has three); the namespace is a Route 53 private zone, about $0.50 a month.
   - (b) Cloud Map **SRV** records with bridge mode: PHP's Redis clients do not resolve SRV, so this needs a resolver shim.
   - (c) Service Connect: an Envoy sidecar in every client task, costing memory on small hosts.
   - (d) A fixed host port on the pinned on-demand host: clients would need the host's address, which changes at every refresh.

   Recommendation: rule (a) as the pattern now, build it in the Tulox package. WP-04 only makes the network mode configurable per task.
9. **Secrets injection.** ECS `secrets` from SSM Parameter Store (the current convention), with the execution role scoped to each service's prefix? Recommendation: yes. The whole-file `wp-config.php` parameters are for WP-05 to split or render at start-up.
10. **Logs.** One log group per service (proposed `/ecs/abd-wordpress/<service>`), with retention of (a) 7, (b) 14 or (c) 30 days. Recommendation: (b) 14 days.
11. **Monitoring.**
    - (a) No Container Insights. Alarm on each service target group's `HealthyHostCount` (free ALB metric), plus an EventBridge rule sending ECS deployment-failure and task-stopped events to `abd-alerts` (free).
    - (b) Container Insights (standard): running task counts and per-task memory, charged as custom metrics and logs, likely a few dollars a month, against the £5 guardrail.

    Recommendation: (a) now; turn on (b) for a week during WP-05 if real per-task memory figures are needed.
12. **Test hostname and listener rule priorities.**
    - Hostname: `hello.abd-wp.uk`, covered by the ALB's existing `*.abd-wp.uk` certificate. Recommendation: yes.
    - Priorities: an explicit `listener_rule_priority` per service in its tfvars, in bands (for example 100s WordPress, 200s Tulox, 900s tests). Recommendation: yes.
13. **Instance refresh and draining.** Managed scaling, managed termination protection and managed draining on the capacity provider, with `scale_in_protected_instances = Refresh` and launch before terminate (100/110). When should the weekly host refresh run? The NAT refreshes on Tuesdays at 04:00, image builds start at 02:00 and rollouts at 04:00. Recommendation: Wednesdays at 03:00.
