# WP-01 Discovery: NAT Instance and S3 Gateway Endpoint

**Date**: 2026-11-10
**Phase**: 1 (Discovery, read-only). Nothing was changed apart from this report.
**Terminology**: the work package's "VPC module" is the `tf-templates/network/vpc` template. There is no VPC module in `abd-cloud-modules`.
**AWS access**: credentials had expired during the code review; the live checks were run on 2026-11-11 and are recorded under "Live checks".

## Summary

The VPC template already does most of what WP-01 asks of it. It has an S3 gateway endpoint, and the production caller already has it switched on. It also has a NAT gateway toggle (`enable_nat_gateway`), which can be turned off without replacing route tables or subnets. The real work is therefore:

1. The NAT instance stack itself (new).
2. Small, backward compatible additions to the `asg` and `launch-template` modules, which currently cannot express a public IP, launch before terminate on an ASG of one, or a lifecycle hook.
3. A careful cutover order, because Terraform's existing `aws_route.private_nat_gateway` will fight the route flip, and destroying it would delete the instance's route (see Risk 1).

One fact in the programme overview is out of date: the production host is a **`t4g.medium` (arm64, Graviton)**, not a `t3.small`. See "Corrections to the programme overview".

## 1. The VPC template

Files: `tf-templates/network/vpc/` (`gateways.tf`, `route-tables.tf`, `s3-endpoint.tf`, `locals.tf`, `outputs.tf`, `variables.tf`).

**Callers** (from `../abd-cloud-params`, `build_resources="network/vpc"`):

| Params target | State key | NAT setting | S3 endpoint | Sequence |
|---|---|---|---|---|
| `abd-global/services-vpc` | `<account>/services/vpc.tfstate` | `enable_nat_gateway = false` | `vpc_endpoint_s3_enable = true` | 2000, protect |
| `abd-wordpress/wordpress-vpc` | `<account>/abd-wordpress/vpc.tfstate` | default (`true`), `single_nat_gateway` default (`true`) | `vpc_endpoint_s3_enable = true` | 2000, protect |

So production (`abd-wordpress`, VPC `10.240.0.0/21`) has **one** NAT gateway and **one** EIP, shared by three private route tables in three AZs.

**Route tables** (`route-tables.tf`):
- Public: the VPC's default route table is adopted as `aws_default_route_table.public`, with `0.0.0.0/0` to the IGW.
- Private: `aws_route_table.private`, `count = max(len(web), len(app), len(cache), len(db))` = 3, one per AZ. Each private subnet type associates with the table at the same index.
- The private default route is a **separate resource**, `aws_route.private_nat_gateway`, `count = enable_nat_gateway ? 3 : 0`, targeting `aws_nat_gateway.this[0]` when only one gateway exists.

**Outputs**: `vpc_id`, `vpc_cidr_block`, `public_route_table_id` (a one-element list), `private_route_table_ids`, the Route53 zone and delegation set IDs, and `db_subnet_group_name`. Nothing outputs the NAT gateway ID or EIP.

**Public IPs**: `map_public_ip` defaults to `false` and neither caller sets it, so instances launched in the public subnets get no public IPv4 address unless the launch template asks for one.

## 2. Can NAT creation be made conditional without replacing route tables?

**Yes, and it already is.** `enable_nat_gateway` gates exactly three resource sets: `aws_eip.nat`, `aws_nat_gateway.this` and `aws_route.private_nat_gateway`. Route tables, subnets and associations are counted from the subnet lists only, so setting `enable_nat_gateway = false` on `wordpress-vpc` would plan to destroy 1 EIP, 1 NAT gateway and 3 routes, and nothing else. No `moved` blocks are needed. The existing `moved.tf` only covers earlier module `[0]` indexing and is unaffected.

This proves the shape on paper only. A `plan` with the toggle off (not applied) is the Build-phase proof.

## 3. VPC endpoint support

Already present and live (`s3-endpoint.tf`): `aws_vpc_endpoint.s3` plus `aws_vpc_endpoint_route_table_association.s3_rt` on every private route table, controlled by `vpc_endpoint_s3_enable` (and `_web_`/`_app_` variants, which create the endpoint but, as written, associate nothing themselves). **Both callers already have it switched on.** WP-01's endpoint work therefore becomes "verify it is live and that S3 traffic bypasses the NAT"; confirmed live on 2026-11-11.

There is no DynamoDB gateway endpoint and no interface endpoint support.

## 4. The ASG and launch-template modules

Files: `abd-cloud-modules/compute/asg/`, `abd-cloud-modules/compute/launch-template/`. The **only caller** of each is `tf-templates/compute/ec2-asg` (used by `app.wordpress`, and by `app.training`, which is marked `prevent`).

**`asg` module**: name, subnets, launch template id and version, sizes, cooldown, grace period, health check type, target groups, termination policies, tags, metrics, and an optional `instance_refresh` block (strategy `Rolling`, `min_healthy_percentage`, `instance_warmup`, triggers). Outputs: `id`, `arn`, `name`.

Gaps for the NAT use case:
- **`instance_refresh_max_healthy_percentage` is declared (default 110) but never wired into the `preferences` block.** `ec2-asg` passes it through to the module, where it is silently dropped. Launching before terminating needs `min_healthy_percentage = 100` with `max_healthy_percentage` above 100 (AWS's own launch-before-terminate setting is 100/110), so this has to be wired in. Wiring it at the default of 110 changes `app.wordpress` from AWS's implicit 100 to 110, which Dave has ruled is intended.
- No `initial_lifecycle_hook` support.
- No mixed instances policy or capacity rebalance (relevant to WP-04 and WP-07 later, not to WP-01).

**`launch-template` module**: AMI, instance type, security groups, SSH key, instance profile, user data, API termination protection. It hard-codes `credit_specification = unlimited`, detailed monitoring on, `ebs_optimized = true`, and `instance_initiated_shutdown_behavior = "stop"`.

Gaps:
- **`require_public_ip` is declared (default `false`) but unused.** There is no `network_interfaces` block, so the template cannot ask for a public IP. Security groups are set through `vpc_security_group_ids`; adding a `network_interfaces` block means moving them into that block, which needs care to avoid a diff for `ec2-asg`.
- `credit_specification = unlimited` will apply to a `t4g.nano`. This is harmless at NAT load, but it is billed if credits run out.

**IAM**: the module takes an existing instance profile name. `ec2-asg` creates its own profile in `iam.tf`, so the NAT stack would follow the same pattern.

## Other observations

- **CI applies `wordpress-vpc` on every push to `main`** (`terraform-apply.yml` line 260), and `terraform-drift.yml` checks it weekly. Combined with Risk 1, this means any merge to `main` between the route flip and the cutover change would point egress back at the NAT gateway.
- `tf-run.sh` applies with `-auto-approve`, so "Dave applies" in the protocol means Dave runs the wrapper or merges to `main`.
- The app host (`app.wordpress`, `t4g.medium`, ASG 1 to 4, instance refresh on tag change) sits in the **private app subnets**, so all its egress (package updates, SES, Stripe and other API calls, GitHub) goes through the NAT today.
- `abd-wordpress/wordpress-vpc/app.ecs` (renamed from `app-ecs` on 2026-11-11) already exists (`compute/ecs-cluster`, marked `prevent`). This is relevant to WP-04, not WP-01.

## Risks

1. **Terraform will fight the route flip, and the cutover order matters.** While `enable_nat_gateway = true`, `aws_route.private_nat_gateway[*]` is in state. Once the NAT instance rewrites the routes, every plan shows drift, and every apply of `wordpress-vpc` (including CI on push to `main`) points them back at the NAT gateway. Worse, setting the toggle to `false` makes Terraform **destroy** those routes. `DeleteRoute` works on table plus destination, not target, so it would delete the instance's `0.0.0.0/0` route and cut private egress until the instance flips again. The fix is to drop the routes from state without destroying them (a `removed` block with `lifecycle { destroy = false }`, available on Terraform 1.15, or `terraform state rm`) before or together with the toggle change. Whether to keep the route resource with `ignore_changes` instead is a Clarify question.
2. **No public IP path.** Public subnets do not map public IPs, and the launch template cannot request one. The NAT instance needs one of these, or an EIP.
3. **The ASG of one cannot launch before terminating** until `max_healthy_percentage` is wired through.
4. **Single NAT, single AZ.** This matches today (one NAT gateway), so it is not a regression, but the route flip makes the AZ choice explicit.
5. **Changing the module defaults** could create a diff for `app.wordpress`, which is production. Every new input must default to current behaviour, proven by a plan on `app.wordpress` and `app.training`.

## Proposed approach

1. **VPC template**: no code changes needed for the endpoint. For the NAT, either use the existing toggle as it is plus a `removed` block for the routes, or add `ignore_changes` on the route's target. Fix the README drift.
2. **`asg` module**: wire `max_healthy_percentage` at its existing default of 110 (ruled 2026-11-11; `app.wordpress` intentionally gains launch-before-terminate refreshes). Add optional `initial_lifecycle_hook`(s), defaulting to none.
3. **`launch-template` module**: an optional `network_interfaces` block when `require_public_ip` is true (associate public IP, security groups in the block). The current path stays unchanged when it is false.
4. **New template** `tf-templates/network/nat-instance` (name per ruling): data-source lookup of the fck-nat arm64 AMI, launch template, ASG of one in a public subnet, security group allowing inbound from the VPC CIDR only, instance role (source/dest-check change on itself, `ReplaceRoute` on the three private route table ARNs, `DescribeRouteTables`, `CompleteLifecycleAction`), user data for the route flip, CloudWatch alarms, and a weekly scheduled refresh. Private route table IDs come from `wordpress-vpc` remote state, as `vpc-peering` does.
5. **New params target** `abd-wordpress/wordpress-vpc/nat-instance` at sequence 2100 or similar, plus its job in `terraform-apply.yml`.
6. **Cutover**: apply the NAT stack, let it flip the routes, verify egress, run a manual refresh, then remove the routes from Terraform state and turn the gateway off after the hold period.

## Questions for Dave (Phase 2: Clarify)

**All answered; the rulings are recorded in the work package under `## Rulings`.**

Each has options and a recommendation. Nothing will be built until these are ruled on.

1. **Third-party allow-listing**: does anything (a payment provider, an API, a client firewall) allow-list the current NAT EIP?
   *If yes, the NAT instance takes over the same EIP (`reuse_nat_ips` already exists for the reverse case). If no, use an auto-assigned public IP.*
2. **One NAT instance or one per AZ?** Today there is one NAT gateway for three AZs.
   *Recommended: one, matching today and the cost goal.*
3. **Packaging the route flip**: (a) fck-nat's built-in options (it supports attaching an ENI or EIP, but route flipping needs its own script), (b) a user data script in this repository, or (c) a script baked by Packer.
   *Recommended: (b), user data in this repository on the stock fck-nat AMI, so nothing new is baked.*
4. **Signalling healthy after the flip**: (a) a launch lifecycle hook completed by the instance after the flip, or (b) EC2 health with a long grace period.
   *Recommended: (a). It is the only way to make "healthy" mean "routes flipped", and the instance refresh then waits for it.*
5. **Ownership of the private default route after cutover**: (a) remove it from Terraform (a `removed` block with `destroy = false`, then the toggle off), so the NAT instance alone owns it, or (b) keep the resource in the VPC template with `lifecycle { ignore_changes = [nat_gateway_id, network_interface_id] }` and a new target input.
   *Recommended: (a). It keeps the VPC template simple, and the route-flip design means the instance is the source of truth anyway.*
6. **Public IP for the NAT instance**: (a) wire `require_public_ip` into the launch-template module (`network_interfaces` block), or (b) switch on `map_public_ip` for the wordpress VPC's public subnets.
   *Recommended: (a). Option (b) changes a subnet attribute for everything in those subnets, including anything launched there later.*
7. **Module interface names**: wiring the existing `instance_refresh_max_healthy_percentage` (default 110, kept), plus a new `initial_lifecycle_hooks` list (or a single hook object) on `asg`. Names and shapes are your call.
8. **Template and params naming**: `tf-templates/network/nat-instance` and `abd-wordpress/wordpress-vpc/nat-instance`, or other names?
9. **DynamoDB gateway endpoint**: add one now (free, needs a small change to the template), or S3 only?
   *Recommended: S3 only. Nothing in `abd-wordpress` uses DynamoDB from the private subnets that I can see.*
10. **Hold period** before turning off the NAT gateway: 48 hours as suggested, or longer to cover a weekly refresh?
    *Recommended: 7 days, so the first scheduled weekly refresh happens while the gateway still exists as a fallback.*
11. **Alerting target**: which SNS topic or alert route should the NAT alarms use? None was found in `abd-wordpress` during discovery.
