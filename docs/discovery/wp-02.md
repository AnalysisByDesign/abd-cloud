# WP-02 Discovery: Codified ECR and CI Push Access

**Date**: 2026-11-11
**Scope**: read-only. Code in `abd-cloud`, `abd-cloud-modules`, `abd-cloud-params`, `abd-cloud-containers`, `abd-cloud-packer` and `tulox`. Read-only AWS calls in `abd-global` (813984516777) and `abd-wordpress` (800653036500), eu-west-1. A `plan` (no `-out`) of `abd-wordpress/account-global/github-deploy`.

## Summary

- An ECR module exists (`compute/docker-repository`), but it is minimal. It has no tag mutability, scanning, encryption or tags inputs, and it always creates a repository policy and a lifecycle policy. Its only caller is the `account` template, which makes one repository per account.
- Both accounts already have a GitHub OIDC provider. In `abd-wordpress`, the provider and two per-repository roles come from the `security/github-deploy` template, which plans clean. That template is the obvious home for push roles.
- The **image generator PoC** (`poc-tulox-image-fleet`) is an AWS Batch fleet in `abd-wordpress`, built by hand. It is the "Tulox POC repository" the work package refers to. Everything it owns is listed in section 3 and is off-limits.
- **WP-03 has already decided most of the naming**, and its CI is waiting for this package. `abd-cloud-containers` pushes `abd/base`, `abd/php`, `abd/laravel`, `abd/wordpress` and `abd/github-runner`. It expects three repository variables: `ECR_REGISTRY`, `ECR_PUSH_ROLE_ARN` and `AWS_REGION`.
- **One conflict to rule on**: WP-03 pushes floating tags (`8.5`, `trixie`), which fully immutable repositories would reject. It also re-pushes the same dated tag when two builds land on the same day. See Q4.

## 4. Consumers waiting on this package

**`abd-cloud-containers` (WP-03, built)**, `.github/workflows/build.yml` and the `Makefile`:
- Repositories it pushes: `abd/base`, `abd/php`, `abd/laravel`, `abd/wordpress`, `abd/github-runner`. These follow WP-03 rulings 2 and 12, namespaced as `abd/<image>`.
- Tags it pushes (WP-03 ruling 13): a floating `<version>` and a dated `<version>-<yyyy.mm.dd>`, plus `-dev` variants for php, laravel and wordpress. For example:
  - `abd/base`: `trixie` and `trixie-2026.11.11`
  - `abd/php`: `8.5`, `8.5-2026.11.11`, `8.5-dev` and `8.5-2026.11.11-dev`
- Consumers outside that repository pin by digest.
- **Architecture**: `linux/arm64` only (WP-03 ruling 24).
- **When it pushes**: on push to `main`, on a nightly schedule (02:00 UTC) and on `workflow_dispatch`. Pull requests build and test only. All pushing runs carry `sub = repo:AnalysisByDesign/abd-cloud-containers:ref:refs/heads/main`.
- **Inputs it expects**: repository variables `ECR_REGISTRY`, `ECR_PUSH_ROLE_ARN` and `AWS_REGION`. Pushing stays off while `ECR_REGISTRY` is empty.
- **Actions it uses**: `aws-actions/configure-aws-credentials` with `role-to-assume`, then `aws-actions/amazon-ecr-login`.

**`tulox`**: `deploy.yml` uses `github-deploy-tulox` for SSM deploys. It doesn't push images yet; that comes with the Tulox session, as `tulox/app`.

| What | Convention |
|---|---|
| Role names | Kebab case, purpose first: `github-deploy-<app>`, `github-actions-terraform`, `rds-enhanced-monitoring` |
| Tags | `local.common_tags` (Account, Owner, Project, SubSystem, Component, Environment, Provisioner = terraform), plus `Purpose` and `Repo` on GitHub roles |
| Account-wide targets | `abd-cloud-params/<account>/account-global/<thing>/`, with `<thing>_config.sh` naming the template and state key |
| Module calls | Relative `source = "../../../../abd-cloud-modules/..."`; `count`- or `for_each`-gated optional features; new inputs default to current behaviour |
| Documents | Policy documents as `data.aws_iam_policy_document`; JSON templates in `files/` |

## 6. Gaps against the target

1. The module can't set tag mutability, exclusion filters, scan on push, encryption or tags. It also can't skip the repository policy, which same-account IAM access doesn't need.
2. There's no template that creates a set of repositories. The `account` template is built for one repository per account.
3. There are no push roles. The OIDC provider in `abd-wordpress` exists and can be reused.
4. There's no pull permission for the WP-04 ECS execution role.
5. There are no outputs that consumers or WP-04 can read: repository URLs, registry host, role ARNs.

## 7. Risks

- **Tag mutability against WP-03's tags.** Fully `IMMUTABLE` rejects the floating tags on every build. Even with the floating tags excluded, two pushing builds on the same UTC day re-push the same dated tag and fail (for example, two merges to `main`, or a merge on the same day as a manual dispatch). See Q4.
- **Registry-level changes reach the PoC.** Enhanced scanning, or a pull-through cache prefix, applies to the whole registry. Prefixes and patterns must avoid `poc-tulox-*`.
- **Lifecycle versus digest pinning.** If an image is expired while a task definition still pins its digest, new tasks fail to start. Retention must outlast the rollout lag.
- **Storage cost.** Nightly no-cache builds create new layers every night: five repositories, two to four tags a day. ECR storage is $0.10 per GB per month, so with a 30-image limit the expected cost is £1 to £3 a month. That's under the £5 guardrail, but retention is what drives it.
- **`github-deploy` runs only by hand** (it isn't in sequence or CI). Adding push roles there keeps them out of drift detection unless the target is added to CI.
- **The OIDC thumbprint lists are hard-coded.** AWS no longer uses them for GitHub's provider, so they're harmless and can be left alone.

## 8. Proposed approach (subject to rulings)

1. **Extend the module** (`compute/docker-repository`), with every new input defaulting to current behaviour so the `account` template plans with no diff:
   - `image_tag_mutability` (default `MUTABLE`) and `image_tag_mutability_exclusion_filters` (default `[]`);
   - `scan_on_push` (default `false`);
   - `encryption_type` (default `AES256`);
   - `tags` (default `{}`);
   - make the repository policy and lifecycle policy conditional on a non-empty document.
2. **A new template** creating a map of repositories with lifecycle rules, and a customer-managed pull policy for WP-04. Placement and name are in Q1.
3. **Push roles** added to `security/github-deploy`, reusing its OIDC provider. Each role is trusted for one repository on `main`, and can push only to that repository's namespace (`repository/abd/*`), plus `ecr:GetAuthorizationToken`.
4. **Outputs**: registry host, repository URLs, the push role ARNs and the pull policy ARN. After the apply, set `ECR_REGISTRY`, `ECR_PUSH_ROLE_ARN` and `AWS_REGION` on `abd-cloud-containers`.
5. **Done when, tested.** Run a test workflow in `abd-cloud-containers` that pushes a throwaway image, then confirm a push outside `abd/*` is denied.

## 9. Questions for Dave (Phase 2)

1. **Where the repositories are defined.** A new template (proposed `tf-templates/compute/container-registry`) with params at `abd-wordpress/account-global/container-registry`, or the existing `account` template extended? Recommendation: the new template. The `account` template is built for one repository per account and mixes in account-wide settings.
2. **Module.** Extend `compute/docker-repository` as in section 8, or create a new module? Recommendation: extend, as the protocol prefers.
3. **Repositories now.** `abd/base`, `abd/php`, `abd/laravel`, `abd/wordpress` and `abd/github-runner` (fixed by WP-03). Create `tulox/app` now as well, or leave it, and the `abd/wp-<site>` repositories, to the Tulox package and WP-05? Recommendation: only the five `abd/*` now. Each later package adds its own.
4. **Tag mutability.**
   - (a) `MUTABLE`: works with WP-03 as built, and consumers pin by digest anyway.
   - (b) `MUTABLE_WITH_EXCLUSION`, with dated tags (`*-20*`) immutable. A dated tag then always means one image, but WP-03's CI must stop re-pushing a dated tag on the same day (for example, by adding a run number to the tag).
   - (c) `IMMUTABLE`: WP-03 would have to drop its floating tags.

   Recommendation: (a) now. Digest pinning already gives the guarantee that tag immutability would add, and (b) can follow if WP-03 changes its tags.
5. **Lifecycle.** Proposal: expire untagged images after 7 days, and keep the newest 30 images per repository by dated tag. That's about a month of nightly builds, which outlasts any rollout pin. The floating tag always sits on the newest image, so it's never expired. Different numbers?
6. **Pull-through cache** for upstream images (Valkey, MySQL, Debian).
   - (a) None for now.
   - (b) ECR Public as the upstream (`public.ecr.aws`, `docker/library/*` mirrors of the official images). No credentials needed; storage only.
   - (c) Docker Hub as the upstream. Needs a Docker Hub account and token in Secrets Manager (about $0.40 a month).

   Any of these is registry-wide, but a dedicated prefix keeps it clear of the PoC. Recommendation: (b), or (a) and leave it to WP-04 if no service needs it before then.
7. **Scanning.** Basic scan on push (free, per repository) only, or enhanced scanning (Amazon Inspector, charged per image, and registry-wide, so it would also scan the PoC)? Recommendation: basic scan on push.
8. **Push roles.**
   - Roles now for `abd-cloud-containers` only? Recommendation: yes; `tulox` and the WP-05 repository add theirs later.
   - Placement: extend `security/github-deploy` with a separate `ecr_push_roles` map, or a new template? Recommendation: extend.
   - Role name: proposed `github-ecr-push-abd-cloud-containers`.
   - Trust: `repo:AnalysisByDesign/abd-cloud-containers:ref:refs/heads/main` only.
9. **CI coverage.** Add `abd-wordpress/account-global/github-deploy` and the new registry target to `sequence/prod.csv` (`protect`) and to the CI plan and drift lists? Recommendation: yes.
10. **Pull permission for WP-04.** A customer-managed IAM policy (proposed `ecr-pull-abd`) whose ARN is output for WP-04 to attach, or only the policy JSON as an output? Recommendation: the managed policy.
11. **Encryption.** `AES256` (free) or a KMS key (about $1 a month plus requests)? Recommendation: `AES256`.
12. **Old repositories** `abd-wordpress` (one 2019 image) and abd-global `docker-repo` (empty). Leave them, as this package's scope says, and list them for the step 7 clean-up? Recommendation: leave them and list them.
13. **The Done when test.** Push the throwaway image as a dated tag to an existing repository (for example `abd/base:ci-test-<date>`, which the lifecycle later removes), or create a dedicated `abd/ci-test` repository with a 1-day expiry? Recommendation: `abd/ci-test`, so real repositories never hold test images.
