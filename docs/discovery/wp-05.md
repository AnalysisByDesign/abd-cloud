## Summary

- **Nine sites, not five or six**: analysisbydesign.co.uk, abd.training, daverix.uk, daverix.ai, rixinteriors.co.uk, blacklit.uk, oranjj.uk, baltihot.co.uk, amyegillin.uk. The domain is the identifier everywhere (SSM path, docroot, EFS dirs, manifest, S3 prefix). daverix.uk only redirects to daverix.ai. rixinteriors.co.uk has no ALB certificate and no delegation: it redirects to a Facebook page from outside this stack (Dave, 2026-11-11), so it is not a site to move.
- **The manifests are live state, not source.** `manifest-sync.sh` installs plugins and themes at boot from `/mnt/efs/manifests/<site>.json`, and `manifest-export.sh` writes the running site back over the manifest **every hour**. Anything changed in wp-admin becomes the manifest. Per-site images need the manifests in Git, and the export loop has to stop for a site once it moves.
- **Premium plugins and themes are unversioned copies on EFS** (`/mnt/efs/premium-{plugins,themes}/<name>`), used whenever `wp plugin install` fails, whatever version the manifest asks for. A build needs a versioned source for them.
- **`wp-config.php` is one SecureString per site** (`/abd-wordpress/<site>/wp-config.php`), written whole at boot. It hard-codes host paths (`WP_CONTENT_DIR=/opt/wordpress/<site>/wp-content`, `W3TC_CACHE_DIR=/var/cache/w3tc`), so it cannot be used unchanged in a container.
- **Mail goes through WP Mail SMTP, installed per site.** The bake-time copy in `/usr/share/wp-stack/mu-plugins/` is never linked into a site, but Dave receives WP Mail SMTP's summaries from each site, so the plugin is installed through the manifests and configured by the `WPMS_*` constants. This matches WP-04's note that WordPress sends straight to IONOS. The host's postfix serves anything still using sendmail.
- **One shared FPM pool**: all nine sites and mortgage share `www` (`pm dynamic`, `max_children 15`). RDS allows about 85 connections, with a 14-day peak of 17 *(D4)*.
- **No listener rules and no EFS access points exist yet.** The ALB forwards everything to the host and nginx does the virtual hosting. Every site already has a test alias, `<sub>.abd-wp.uk`, covered by the base certificate.

## 1. Boot-time update process (abd-cloud-packer)

Order, all oneshot, all `RequiresMountsFor=/mnt/efs`:

1. EFS `fs-38536ff0:/` at `/mnt/efs` (TLS), with config bind-mounted over `/etc` (`files/fstab.efs`).
2. `wordpress-secrets-init`: `wp-secrets-init.sh` writes each site's `wp-config.php` from SSM, and the postfix `sasl_passwd` to EFS. It always exits 0, so a missing parameter leaves a site with no config and nothing notices.
3. `wordpress-manifest-sync`: `manifest-sync.sh`, all nine sites in parallel behind a bare `wait`, so its exit status ignores per-site failures. Per item: `wp plugin install NAME --version=V --force`, else copy the premium directory from EFS, else a warning. It activates `active` items but never deactivates or removes anything. Needs wordpress.org at boot.
4. `wordpress-wellknown`: rewrites `robots.txt`, `humans.txt` and `.well-known/security.txt` in every docroot.
5. php-fpm, nginx, postfix.

Core is not updated at boot: it is baked (WordPress 7.1.4, checksums verified), with `wp-content` excluded. `min-versions.env` is a bake-time PHP floor only.

Hourly cron, `manifest-export.sh`: refuses to run until the sync's stamp file exists, then rewrites `/mnt/efs/manifests/<site>.json` (adding `site`, `generated` and `wordpress_version`). The 2026-07-09 incident shows a half-built instance can still overwrite good manifests.

The S3 copy of each manifest is inside the daily backup tarball (`s3://abd-wordpress-html/archive/<site>/<date>/configs.tar.gz`, GLACIER_IR), not a plain file.

## 2. Per-site layout and configuration

- Docroot `/opt/wordpress/<site>/` on the root volume. Plugins and themes are local and writable by `nginx` (so wp-admin can update them). `wp-content/uploads` and `wp-content/w3tc-config` are symlinks to `/mnt/efs/uploads/<site>` and `/mnt/efs/w3tc-config/<site>`.
- `wp-config.php` contents are not in any repository. Documented as present: `DB_*`, `W3TC_CACHE_DIR`, `WP_CONTENT_DIR`, `WP_CONTENT_URL`, `WPMS_*`. Not referenced anywhere, so unknown: salts, `WP_CACHE`, `DISALLOW_FILE_*`, `DISABLE_WP_CRON`, `table_prefix`, and how HTTPS behind the ALB is detected.
- nginx WordPress server blocks (`provision.sh:827-867`): `listen 80`, `try_files ... /index.php?$args`, long expiry on static assets, `.well-known` allowed, dotfiles denied. Unlike the Tulox and mortgage blocks, they have no `set_real_ip_from`, no `fastcgi_param HTTPS on`, no HSTS, no W3TC rewrites and no xmlrpc or `wp-config` deny rules. The live `sites-enabled` on EFS may differ.
- PHP 8.3 with bcmath, gd, mbstring, mysqlnd, opcache, pdo, xml, intl, zip and imagick. `memory_limit` comes from the live php.ini on EFS (probably the 128M default; not visible).

## 3. Writes outside uploads

| Path | Today | Container note |
| --- | --- | --- |
| `/var/cache/w3tc` | Local, shared by all sites, lost on refresh | Ephemeral already: tmpfs or the task's own writable layer |
| `wp-content/w3tc-config` | EFS, per site | W3TC writes its settings here from wp-admin, which `DISALLOW_FILE_MODS` does not stop. Needs to stay writable and persistent |
| Plugins and themes | Local, writable | Immutable in the image |
| `wp-content/upgrade` | Local | Not needed with `DISALLOW_FILE_MODS` |

No Wordfence, `wflogs` or other plugin cache paths are referenced in code. Anything a plugin writes under `wp-content/` today lands on the local disk and is lost at each refresh, so it is already ephemeral. The manifests will confirm which plugins are in play.

## 5. Infrastructure (abd-cloud, abd-cloud-params)

- **ALB** `abd-wordpress-ec2-asg`, owned by the `app.wordpress` state. Port 80 redirects to 443; 443 forwards to one instance target group on port 80. No listener rules *(D4)*. 11 certificates: the base `abd-wp.uk` and `*.abd-wp.uk`, plus one per site except rixinteriors.co.uk.
- **DNS per site** (`network/dns`): apex alias to the ALB, `www` CNAME to the apex, and `<sub>.abd-wp.uk` alias to the ALB. tulox.uk and tulox.co.uk share the same ALB.
- **EFS** `abd-wordpress-html`, bursting, no access points. Files are owned by `nginx:nginx`; the images run as 10001 (UID of `nginx` on EFS not verified).
- **RDS** MySQL 8.4 (8.4.11 in AWS, 8.4.7 in tfvars), `db.t3.micro`, single AZ, 7-day automated backups. Parameter group `rds-manual-8-4` is not in Terraform; `max_connections` about 85 *(D4)*. Per-site schemas and users are not in Terraform and appear only inside the SSM `wp-config.php` values. No `MAX_USER_CONNECTIONS` anywhere.
- **Secrets**: SSM Parameter Store only. The host role reads `/abd-wordpress/*` and `/laravel/*`.
- **Host**: `t4g.medium`, ASG 1/1/4, latest `abd-wp-php83-*` AMI. No scheduled refresh on this host (only the NAT has one); the "weekly host refresh" in WP-05's Done when means the planned ECS hosts (WP-04 ruling 13).
- **ECR**: no `abd/wp-<site>` repositories yet (deferred here by WP-02). The `abd-cloud-containers` push role covers `repository/abd/*`, so it could push them; another repository would need its own `ecr_push_roles` entry.

## Gaps against the target

- No source-controlled manifests, and no versioned source for premium items.
- `wp-config.php` paths and mail are host-specific.
- No listener rules, access points, per-site repositories or deploy roles.
- No smoke test or nightly for site images; the `abd/wordpress` smoke test (WP-03) boots core against a throwaway MySQL and is the obvious base.

## Risks

- **Manifest drift during the overlap**: the hourly export keeps rewriting manifests from the old host. A site edited in wp-admin after its snapshot diverges from its image.
- **Mail**: any site whose WP Mail SMTP is not configured falls back to sendmail, which a container does not have. The `wp-config.php` read confirms every site sets `WPMS_ON`.
- **Uploads ownership**: an access point presenting 10001 cannot write into directories owned by `nginx`. Changing ownership in place would break the old host's writes, and with them the rollback path.
- **HTTPS detection**: without `X-Forwarded-Proto` handling, WordPress behind the ALB can loop on redirects or serve mixed content. How the host avoids this today is not visible.
- **RDS connections**: nine services plus Tulox against about 85 connections on a `db.t3.micro`.
- **Not WP-05, noted in passing**: `abd-cloud-params/abd-wordpress/wordpress-vpc/db.wordpress/db_config.tfvars:19` holds a plaintext `admin_password` in Git (ignored by Terraform after creation). Worth rotating and removing.

## Proposed approach (subject to rulings)

1. Snapshot the nine manifests into Git. Premium zips go to a versioned private S3 prefix, referenced by version.
2. Per-site image `FROM abd/wordpress:<php>` that applies the manifest at build time, bakes the well-known files, and ships a `wp-config.php` reading everything from environment variables (DB, salts, mail, URLs), with `X-Forwarded-Proto` handling and container paths.
3. Per-site SSM parameters split from the current whole-file one, injected as ECS `secrets`.
4. Mail to WP-04's relay through a small mu-plugin that points PHPMailer at `smtp.abd-wordpress.internal`.
5. EFS access point per site at a **new** directory owned by 10001, filled by `rsync` from the old one at cutover, so the old host's tree stays intact for rollback.
6. daverix.uk as an ALB redirect rule, no task.
7. Pilot on the quietest site (from the traffic numbers), weighted rule, then the rest one at a time, removing each from `manifest-sync` and `manifest-export` as it moves.
